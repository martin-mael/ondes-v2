## How the owner works (unchanged, and it worked again in wave 8)

1. **Launch.** One issue = one session (`start_session`, fresh context, its own worktree, branch `<issue>-<slug>`). Each brief:
   - lists the ADRs to read and the paths the session owns;
   - names who it coordinates with, by session name (`w9-<issue>-<slug>`), and says to find them with ListAgents;
   - assigns its ADR number;
   - repeats the dev-stack rules and the UI rules;
   - says it may use Haiku subagents for chores, and that it opens one PR, moves the issue to "In review", and never merges.
2. **Review.** Two Haiku reviewers per PR, run as `Agent` with `model: haiku` in the background: one looks for bugs, the other checks acceptance criteria, conventions and tests. Spot-check the high findings in the code yourself, then present one triaged list per PR. The owner said "fix all, including minor" again. Send each session its list with `SendMessage` (to its `local_…` id), and tell it to push back with reasons where it disagrees.
3. **Integrate** into `mN-wave-K` off main:
   - merge each branch;
   - resolve additive conflicts with `tools/resolve.py`;
   - regenerate migrations with `tools/regen-migrations.sh` after each conflicting journal;
   - add the glue the sessions ask for;
   - run everything;
   - open one combined PR.
4. **The owner tests locally** before merging (see "Running the app" in the previous handoff). Fix their feedback on the wave branch: small subagents in parallel on disjoint paths, told not to commit; you commit each fix separately.
5. **Merge** only when the owner says so: squash, close the originals as superseded, and delete their branches. `gh pr close --delete-branch` did **not** delete the remote branches this time; run `git push origin --delete <branches>` and check with `git ls-remote`.
